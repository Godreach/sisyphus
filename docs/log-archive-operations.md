# 日志归档恢复与清理

日志状态与任务执行结果独立。Agent 即时上传最多尝试三次，每次最多 30 秒；失败后上报原执行结果并释放计算槽位，不因归档故障自动重跑构建。Agent 每 30 秒扫描持久待归档标记，后台单次上传最多 5 分钟（给大日志传输更长窗口，同时避免一个挂起请求永久阻塞其它 attempt），重启后继续补传，Server 确认前不删除本地正文。工作区根不得与日志缓冲目录重叠或互相包含，以免工作区清理触及封存副本。

单任务默认截断上限为 1 GiB，截断不会使任务失败。Agent 的 `--log-buffer-capacity-gib` / `SISYPHUS_LOG_BUFFER_CAPACITY_GIB` 默认 20 GiB；实际缓冲文件（含封存副本）达到容量的 90% 后停止接新任务，运行中的任务继续执行。缓冲占用、待确认 attempt 数、最后归档错误和报告时间可在管理员的 Agent 详情查看。压力解除后恢复派发。

管理员可在 Agent 详情对待归档日志填写原因并确认“标记永久丢失并清理”。列表优先显示待归档记录，每页 500 条，可加载更多历史记录。该决定与 `log_archive_lost` 审计事件同事务提交，保留最后序号、归档大小、执行结束时间和 Agent 最后心跳。不要把短暂离线当作永久丢失。Server 撤销发布资格并清理已收到的临时对象；Agent 重连补传时收到丢失确认，随后清理本地副本。构建结果不变。

新日志归档的 `[retention] log_retention_days`、`--log-retention-days` 或 `SISYPHUS_LOG_RETENTION_DAYS` 默认 30 天，独立于既有 `retention_days`。从 Agent 执行结束时刻起算，归档上传、重试、查看和同构建的新 attempt 不延长旧日志寿命。旧 SQLite 日志仍按原 per-build 规则清理，不在启动时迁移。

日常清理低频扫描到期归档，手动清理终态构建立即撤销该构建日志并删除正文和索引。S3 删除失败保留登记，下一轮重试。清理后保留状态墓碑，迟到上传不可重新发布日志；日志页面显示清理或丢失原因。备份须同时覆盖 Server SQLite/归档后端和仍持有未确认正文的 Agent 数据目录。
